## Project Overview

Swish is a Clojure-like Lisp implementation designed to integrate seamlessly with Swift and the Apple developer ecosystem. The goal is to bring Clojure's powerful features (persistent data structures, functional programming idioms, homoiconicity, macros) to iOS, macOS, and other Apple platforms.

## Architecture

### Environment Hierarchy

The evaluator uses a two-tier environment chain:

- **Core environment** (`Evaluator.coreEnvironment`): holds built-in symbols and
  functions (e.g. arithmetic operators, `nil`, `true`). Populated at startup;
  user code should not shadow these at the global level.
- **Global environment** (`Evaluator.environment`): holds user-defined bindings
  created with `def`. Its parent is the core environment, so lookups fall
  through to core when a name isn't found globally.

Child environments (for `let` bindings, function calls, etc.) will be created
with the global environment as their parent, forming a full lexical scope chain.

### Lazy Sequences

Swish supports genuine lazy sequences via `LazySeqBox` (`Sources/SwishKit/LazySeqBox.swift`). A `.lazySeq(LazySeqBox)` case in `Expr` holds an unrealized thunk. Forcing the box produces a head/tail pair (or empty). Thunks run at most once (memoized). `lazy-seq` is a special form (not a macro) that captures the body and lexical environment.

- Infinite producers (`range`, `iterate`, `cycle`, `repeat`, `repeatedly`) are defined in `core.clj`.
- `map`, `filter`, `concat`, `mapcat`, `lazy-cat` are defined lazily in `core.clj` and shadow the bootstrap native registrations after core loads.
- `*print-length*` (default 1000) caps how many elements the printer realizes before emitting `...`. The `Printer` struct exposes `printLengthCap: Int?` to control this.
- `unquote-splicing` handles lazy seqs by fully realizing them (so macros like `lazy-cat` that use `~@(map ...)` work correctly).

### Transducers

Swish supports Clojure-style transducers (Clojure 1.7+).

- `reduced` is a new `Expr` case `case reduced(Expr)` — a sentinel signalling early termination from `reduce`. Native functions `reduced`, `reduced?`, `unreduced`, `ensure-reduced` are registered in `CoreHOF.swift`. `deref` on a `reduced` value returns the wrapped value.
- `reduce` (`CoreHOF.swift`) iterates lazily (handles `.lazySeq` without materializing) and checks for `.reduced` after each step to break early.
- `volatile!`/`vswap!`/`vreset!` are atom aliases in `core.clj`. Stateful transducers (`take`, `drop`, `partition-all`, etc.) store per-invocation state in atoms created inside their 1-arity closure.
- `comp`, `completing`, `transduce`, `into` (3-arity), and all 1-arity HOF transducer forms are defined in `core.clj`.
- `sequence` is lazy: each input element steps through the transducer with a fresh `[]` accumulator; outputs are collected and drained lazily. The 1-arity completion `(rf [])` flushes buffered state after input exhaustion. Infinite seqs + `(take n)` terminate correctly via `reduced`.
- `eduction` delegates to `sequence`; calling `eduction` creates fresh transducer state, but the returned lazy seq cannot be re-reduced independently.

## Known Limitations (to address later)

### Common core forms that were missing entirely, now implemented (two batches)

A systematic audit (direct eval of each candidate, not just grepping source — grep alone gives false negatives for Swift-native/special-form registrations) found `dotimes`, `while`, `condp`, `declare`, `cond->`, `cond->>`, `as->`, `some->`, `some->>`, `memoize`, and `trampoline` completely missing — confirmed by `Undefined symbol` on direct eval, not documented anywhere in this file previously. Unlike most of this file's entries, these aren't deliberate JVM-hierarchy-driven simplifications — they're common, general-purpose Clojure forms that were simply never ported. All 11 are implemented in `core.clj` as straightforward, faithful ports of real Clojure's own source (no Swift/native code, no new `Expr` case), placed alongside their conceptual siblings (`condp` next to `cond`, the five threading macros next to `->`/`->>`, `dotimes`/`while` next to `doseq`, `declare` next to `defonce`, `memoize`/`trampoline` at the end of the Higher-Order Functions section).

A second audit pass found a further batch, likewise implemented as faithful ports: `mapv`, `filterv`, `reduce-kv`, `partition-by`, `distinct?`, `every-pred`, `reductions`, `when-some`, `if-some`, `doto`, `bound?` (all pure `core.clj`), `clojure.set/rename-keys` (`set.clj`), `clojure.walk/keywordize-keys`/`stringify-keys` (`walk.clj`), and three needing small new native Swift: `ns-resolve` (`CoreNamespace.swift`, reusing the existing `resolveVar(name:in:)`/`the-ns` machinery, parameterized by the passed namespace instead of the current one) and `clojure.string/index-of`/`last-index-of` (`CoreStringNS.swift`, via Swift `String.range(of:)`/`.backwards`, returning `nil` — not −1 — when not found, matching Clojure and Swish's own convention). `partition-by` and `reductions` are written as single self-recursive `lazy-seq`s (not composed lazy layers) for the stack-depth reasons documented under `range`/`clojure.walk` — verified stack-safe under the test runner at 5000/10000 elements. `partition-by`'s 1-arg stateful-transducer form buffers with a `(volatile! [])` rather than real Clojure's `java.util.ArrayList`, the same adaptation `partition-all` already makes. Two deliberate, documented divergences in this batch: `bound?` checks **root**-boundness only (`var-has-root?` → `Var.isBound`), not thread-local bindings (which live in `bindingFrames`, invisible to it) — matching real Clojure's `.hasRoot` rather than its `bound?`; and `ns-resolve`'s 3-arg `(ns env sym)` form accepts but ignores the `env` local-binding map (Swish does no local-env var capture there).

Two small dependency gaps surfaced and were closed the same way, for the same reason (staying maximally faithful to upstream rather than rewriting the caller around a missing dependency): `split-at` (needed by `condp`'s real algorithm) didn't exist either and is now a real port (`[(take n coll) (drop n coll)]`), and `unchecked-inc` (used by real Clojure's `dotimes` as a JVM boxing-avoidance hint with no behavioral effect) has no Swish equivalent worth porting — `dotimes` uses plain `inc` instead, which is exactly equivalent since Swish integers are already 64-bit (see the `abs.cljc` overlay's comment in `support/clojure/core_test/`).

`memoize` deliberately uses `find`/`val` rather than `get` to probe its cache, matching real Clojure — this is the one correctness-relevant detail worth calling out: `get` can't distinguish "this argument list was already memoized, and the cached result happens to be `nil`" from "this argument list has never been called," which would cause a memoized nil-returning function to be needlessly re-invoked on every call. `find` returns a real map entry (or `nil` if the key is truly absent) that makes this distinction correctly.

`definline` remains unimplemented, deliberately: it declares an inline-expansion form for a JIT/bytecode compiler to substitute at call sites, and Swish is a tree-walking interpreter with no such compilation pass to hook into — there's no faithful behavior to port, unlike the 11 forms above.

### Multimethods

`defmulti`/`defmethod` are implemented (`core.clj`, "Hierarchies" and "Multimethods" sections near the end of the file), including full hierarchy-based dispatch (`derive`/`underive`/`isa?`/`parents`/`ancestors`/`descendants`/`make-hierarchy`) and ambiguity resolution (`prefer-method`/`prefers`). `clojure.test/report` and `clojure.test/use-fixtures` (`test.clj`) have been converted from their earlier `cond`-based workarounds to real multimethods.

The whole feature is pure Swish/Clojure code — no new `Expr` case or native Swift function. A multimethod's method table and prefer table are plain atoms; the callable multimethod itself is an ordinary variadic closure with those atoms attached via function metadata (`with-meta`/`meta` on a function mutate/read the same underlying reference, confirmed in `CoreMeta.swift`); `isa?`/`parents` are called directly since dispatch resolution is just Swish code calling other Swish code, with no Swift/Clojure boundary to cross the way real Clojure's Java `MultiFn` calls back into Clojure vars.

Two deliberate divergences from real Clojure, both direct consequences of Swish having no JVM class hierarchy (same root cause as the Protocols section below):
- **No method-resolution cache.** Real `clojure.lang.MultiFn` caches resolved dispatch-value → method lookups and invalidates on hierarchy change; Swish's `mm-find-method` just re-runs the linear best-match scan across the whole method table on every dispatch. Semantically identical, just O(n) in method count instead of O(1) after the first call — consistent with `case`'s existing O(n) dispatch (this file has no O(1) dispatch machinery anywhere else either).
- **`ancestors`/`parents` reflect a `deftype`/`defrecord`'s declared protocols, but not automatic Java-class inheritance.** Real Clojure's hierarchy functions walk both a class's actual superclass/interface chain *and* its implemented protocols (via JVM reflection over the generated interface) when `tag` is a class. The class-inheritance half is still out of scope — Swish has no class objects to walk — but the protocol half is now implemented (`protocols-of`, `core.clj`'s Hierarchies section): a real O(all interned vars) scan, since there's no existing type→protocols index to look up directly (each protocol's own var only holds the forward protocol→implementing-types map, the same one `satisfies?`/`extenders` read) — measured at ~5.7ms/call against 461 vars in a freshly-booted environment, linear in var count. `derive`-based relationships work fully either way, including using a `deftype`/`defrecord`'s type identity as a plain derive tag (they're already keywords).

  **`isa?` deliberately does not get this protocol-awareness** — confirmed by reading its source (`(contains? ((:ancestors h) child) parent)`, a raw hierarchy-map lookup that bypasses the `ancestors` function entirely), so adding the scan to `ancestors`/`parents` cannot affect `isa?`-driven multimethod dispatch performance. This had one real, easy-to-miss consequence during implementation: `mm-prefers?` (multimethod ambiguity resolution, below) calls `parents` *directly*, not just `isa?` — initially missed, and wiring the protocol scan through it caused a genuine stack overflow under Swift Testing's smaller-stack runner thread (the recursive `mm-prefers?` walk compounding with each `parents` call's now-larger frame, not the scan's own O(n) cost — a neutralized, empty-returning `protocols-of` reproduced the crash just as reliably as the real one, isolating the cause to call-site depth, not scan cost). Fixed by having `mm-prefers?` read `(:parents h)` directly instead of calling the public `parents` fn — which turns out to match real Clojure's own `MultiFn.prefers()` more faithfully anyway (it accesses the hierarchy's internal parents map directly, never the public `clojure.core/parents`), not just a workaround.

`clojure.test/assert-expr` — once a separate, unrelated gap in `is`'s architecture — has since been implemented as a real multimethod; see the "`clojure.test` — `assert-expr` / `try-expr`" section below.

### Protocols

`defprotocol`, `deftype`, `extend`, `extend-type`, `extend-protocol`, `satisfies?`, `extends?`, `extenders`, `instance?` are implemented (`Evaluator+Defprotocol.swift`, `Evaluator+Deftype.swift`, `CoreProtocol.swift`), and `defrecord` (`Evaluator+Defrecord.swift`) now parses and registers trailing protocol-implementation clauses it previously discarded. Protocols can be extended onto both `deftype`/`defrecord` types **and built-in types**. The remaining divergence from real Clojure is a direct consequence of Swish having no JVM class hierarchy:

- **Extending protocols onto built-in types is supported, via type-name vars + a data-modeled `Number`/`Object` hierarchy** (not the JVM class graph). `core.clj` binds a var for each built-in type name to the dispatch keyword the runtime already produces (= the value's `type`, i.e. its `Expr.description`) — `(def String :string)`, `(def Int :integer)`, `(def Vector :vector)`, `(def Number :Number)`, `(def Object :Object)`, etc. — so `(extend-type String P …)`/`(extend-protocol P Int … Double …)`/`(instance? Number 3)` resolve their type argument to a keyword exactly as a `deftype` type-var does, with no change to how `extend`/`extend-type`/`instance?`/`extends?` resolve types. **Naming is deliberately Swift-first, not Java:** scalars use their honest underlying Swift type name (`String`/`Int`/`Double`/`Float`/`Bool`/`Character` — a Swish string *is* a Swift `String`, etc.), which is forward-compatible with eventual Swift/ObjC interop and avoids inventing fake `java.lang` names (the "no fake JVM symbols" rule); persistent collections and Clojure-native scalars, which have no Swift-stdlib equivalent, use Swish-native names (`Vector`/`List`/`Map`/`Set`/`Seq`/`Keyword`/`Symbol`/`Ratio`/`BigInt`/`BigDecimal`). `Long`/`Integer`/`Boolean` are intentionally absent (use `Int`/`Bool`, or a `:swish` overlay for ported code). Dispatch (`protocol-dispatch`, `core.clj`) checks the exact type key first, then walks a fixed built-in ancestor table (`builtinAncestors`, `CoreProtocol.swift`, exposed to core.clj as the internal `builtin-ancestors`): numerics → `[Number, Object]`, everything else → `[Object]`, `nil` → `[]` (so `nil` never falls back to `Object`, matching Clojure/Java where `null` is not an `Object`; `(extend-type nil …)` remains its own separate slot). This mirrors real Clojure's `find-protocol-impl` walking the class chain, just backed by data. `satisfies?`/`extends?`/`instance?` respect the same table. `nil` still dispatches as `"nil"`, and `deftype`/`defrecord` types fall back to `Object` too (so `(extend-type Object …)` is a universal non-`nil` default). Swish's `:impls` is still a single unified registry for inline (`deftype`/`defrecord`-declared) and `extend`-added implementations, unlike Clojure's separate generated-interface fast path — making `satisfies?`/`extends?`/`extenders` simpler than their real-Clojure counterparts. **Scoped simplifications:** sorted collections and map-entries are distinct dispatch keys (`:sorted-map`/`:sorted-set`/`:map-entry`), so extending `Map`/`Set`/`Vector` does *not* catch them (real Clojure's interface hierarchy would); and the hierarchy is the fixed `Number`/`Object` table only — no arbitrary user-defined built-in ancestry. Real ObjC/Swift class-hierarchy dispatch (for genuine `NSObject`/`NSNumber` instances) is a deliberate *future* concern: it will arrive as an **additive** foreign-object `Expr` case bridged at the interop boundary, whose dispatch can consult the object's real runtime hierarchy — not a rewrite of the value-representation `enum` (the enum + data-table was a deliberate architecture choice, confirmed with the user).
- **`ancestors`/`parents`** (the multimethod hierarchy fns, see the Multimethods section) are *separate* from this protocol-dispatch table and unaffected by it; they reflect a type's declared protocols but not the built-in `Number`/`Object` protocol-dispatch ancestry. Because Swish binds `Object` as an ordinary keyword tag rather than a class, `(descendants Object)`/`(ancestors Object)` no longer throw the way real Clojure's "can't get descendants of classes" does — the jank suite's `descendants`/`ancestors`/`parents` fixtures carry `:swish` overlays (`support/clojure/core_test/`) dropping those class-throwing assertions, same as they already did for the class-inheritance cases.

Also deferred: **mutable `deftype` fields** (`^:unsynchronized-mutable`/`^:volatile-mutable`). `set!` now exists for thread-bound dynamic vars (see the `set!` section below), but the **mutable-field form** of `set!` — which is what these annotations would need — is still unimplemented, since it requires per-instance mutable field storage the type doesn't have. The annotations parse without erroring, so well-formed Clojure code doesn't break, but fields are immutable this pass.

`deftype`/`defrecord` method bodies get real Clojure's unqualified field access (a field like `radius` is directly in scope inside a type's own methods, without needing `(.radius this)`) via a synthetic `let` injected ahead of each method body, binding each declared field from the method's first parameter — this only applies to *inline* (the type's own trailing clauses) methods, matching real Clojure, where retroactive `extend-type`/`extend-protocol` methods do *not* get direct field access either.

### `set!` is implemented for thread-bound dynamic vars only

`set!` (`evalSet`, `Evaluator+Binding.swift`, a special form dispatched alongside `binding` in `Evaluator.swift`'s `evalList`) implements just the `(set! var-symbol value)` form — mutating the current thread-local binding of a dynamic var established by `binding`, e.g. `(set! *print-length* 50)` inside a `binding` scope. Previously it didn't exist at all (confirmed — it was already listed in `special-symbol?`'s name table in `CorePredicates.swift` but had no evaluator handling and wasn't in `specialFormNames`). It's a faithful port of Clojure's `Var.doSet`: the target var must be **thread-bound** (present in an active `binding` frame) or it throws Clojure's "Can't change/establish root binding of: … with set" — implemented by scanning `bindingFrames` for the innermost frame holding the var and mutating that entry, leaving the root value untouched. The target var is resolved exactly as `binding` resolves its targets (`resolveQualifiedVar` then `resolveVar(name:in:)`), so it behaves identically under alias-expansion (a `set!` inside a `fn`/`defn` body resolves the qualified target correctly — covered by a test).

Two deliberate design points:
- **No explicit `isDynamic` check.** A non-dynamic var can never be thread-bound (`binding` rejects non-dynamic vars up front), so `set!` on one naturally falls through to the same "root binding" error — matching real Clojure, which likewise only distinguishes thread-bound from not, not dynamic from not, at the `set!` call site.
- **No validator/watch involvement.** Clojure's dynamic `set!` path (`Var.doSet`) notifies no watches, and Swish's `Var` has no validator field at all — so `set!` is a plain frame mutation returning the new value, with nothing to validate or notify. (This is unlike `alter-var-root`/atoms/refs, which do fire watches.)

The **mutable-`deftype`-field form** of `set!` (`(set! field new-val)` inside a type method with `^:unsynchronized-mutable`/`^:volatile-mutable` fields) is **still unimplemented** — that needs per-instance mutable field storage the type doesn't have (see the Protocols section's mutable-fields note above), and is a separable piece of work. Java field/static assignment forms (`(set! (. obj field) v)`) are out of scope permanently (no Java interop) and throw a clear "target must be a symbol" error.

### `reify` creates anonymous protocol instances that close over the lexical env

`reify` (`evalReify`, `Evaluator+Deftype.swift`, a special form dispatched alongside `deftype`/`extend-type` in `Evaluator.swift`'s `evalSpecialForm`) implements `(reify Protocol1 (m1 [this a] body)... Protocol2 (m2 [this] body)...)`: one anonymous instance implementing the given protocols, whose method bodies **close over the surrounding lexical environment** — the defining difference from `deftype`, whose methods only see the type's fields + globals. Previously entirely absent (only a name-table entry in `CorePredicates.swift`'s `specialSymbolNames`). Adding it as one more special-form case is what forced the `evalList`→`evalSpecialForm` switch extraction documented in the `evalList` performance section below (a debug-build stack-frame issue, not anything reify-specific).

The whole feature reuses the existing protocol machinery — no new `Expr` case, matching the Protocols/Multimethods/`ex-info` precedent:
- **Lexical closure comes for free.** `buildProtocolMethodImpls(_, in: env, ...)` already builds each method as a `SwishFunction` with `capturedEnv: env`; `evalReify` just passes the *local* `env`, so methods capture locals. `deftype`/`extend-type` pass a more global env, which is exactly why their methods don't get this — the divergence is only in *which* env is captured.
- **Per-instance inline method table, not `:impls` registration.** Because reify methods capture *per-evaluation* locals, two evaluations of one reify form need distinct closures — a shared, type-name-keyed `:impls` entry can't hold both, and per-evaluation registration would leak entries and mutate global protocol vars as a side effect of evaluating an expression. So each instance instead carries its own method table. It's represented as an anonymous `.deftype(typeName: <gensym>, fields: [], data: {reifyMethodsKey → method-map, reifyProtocolsKey → protocol-name-set})` (reserved `__swish_reify_*__` keys, defined in `Evaluator+Deftype.swift`). `printDeftype` iterates only declared `fields` (empty here), so a reify instance prints cleanly as `#reify__N[]` with no closures dumped — no printer changes. `.deftype` instances aren't associative in user code, so the stashed table is invisible to user introspection (and `deftype-field-value` only reads declared fields, of which reify has none).
- **Dispatch and `satisfies?` are the only runtime touch-points.** `protocol-dispatch` (`core.clj`) gets a fast-path: a native `reify-method-table` (`CoreProtocol.swift`) returns the instance's inline method map (or `nil` for anything else — so non-reify dispatch is unchanged, at the cost of one extra O(1) native call per protocol dispatch). `satisfies?` (`coreSatisfies`) checks a reify instance's protocol-name set by the protocol's qualified `:name`. `instance?`/`extends?`/`extenders`/`type` need no changes (reify registers no named type).
- **Alias-expansion needs a `reify`-aware clause (`expandReifyForm`, `Evaluator+AliasExpansion.swift`).** A `reify` inside a `fn`/`defn` body is rewritten by `expandAliases` at definition time; the generic list-recursion would treat each `(mname [params] body...)` clause as a call and qualify the *method name* `mname → ns/mname`, so the per-instance table would be keyed under a qualified name while `protocol-dispatch` looks up the bare keyword — a silent dispatch miss (it manifested exactly as a `reify`-in-`defn` test failing while the bare-`let` case passed). `expandReifyForm` qualifies only the leading protocol symbols and leaves each method clause untouched; the clause bodies are (re)expanded correctly at reify-eval time by `buildProtocolMethodImpls`→`buildFnArity`, which sees the right locals (via `env.allNames()`). This is the same `quote`/`case`/`fn`/`let`-style special-casing that list already needs — `deftype`/`defrecord` have the identical latent hazard but never hit it in practice (they're effectively always top-level, never nested in a `fn` body the way `reify` routinely is).

Deliberate divergences:
- **`type` returns a per-instance gensym keyword** (`:reify__N`), so `(= (type r1) (type r2))` is `false` even for two instances of the *same* reify form — real Clojure compiles one class per reify *form*, so those would be equal. Each Swish reify evaluation is its own anonymous type.
- **Only Swish protocols are supported**, not `Object`/interface methods (`toString`, etc.) — Swish has no JVM classes/interfaces to implement, the same root cause as the Protocols section's other limitations.
- **Methods are merged into one table across all implemented protocols; same-named methods across protocols resolve last-wins**, with no conflict detection (real Clojure would reject the collision). Method lookup on the instance is by name across the merged table.

### STM (Software Transactional Memory)

`ref`, `dosync`, `ref-set`, `alter`, `commute`, `ensure` are implemented (`SwishRef.swift`, `Evaluator+STM.swift`, `CoreRef.swift`), using optimistic concurrency control with three deliberate simplifications vs. real Clojure:

- **Conflict detection covers every touched ref, not just written ones.** Commit verifies the version of every ref read *or* written by the transaction, not just Clojure's narrower write-focused read-set. This is strictly conservative (never wrong, only possibly more retries under contention) and has two consequences: `ensure` reduces to a transactional read that requires an active transaction, and `commute` reduces to `alter`'s full conflict-checked behavior (giving up Clojure's relaxed/deferred-to-commit throughput optimization for commutative ops, since it's untested anywhere). Note: real Clojure's plain `deref` inside a transaction is *not* conflict-checked at all — only `ensure`/`alter`/`ref-set` are — meaning Clojure itself permits write-skew that `ensure` exists specifically to prevent. Swish's blanket check-everything-touched approach is actually the *stricter* of the two on this specific point, not the laxer one.
- **A single global commit lock**, not per-ref lock ordering. Transaction *bodies* run fully unlocked/concurrently; the lock is held only for the brief two-phase verify-then-write commit (verify all touched refs' versions first, then write only if every check passed — never interleaved, to avoid partially committing a transaction that's actually aborting).
- **No per-ref locking or age-based "barging."** Real Clojure locks each `Ref` individually and uses barging — an older transaction can force-abort a younger competitor holding a lock it needs — to avoid livelock. Swish's single global commit lock plus plain retry-from-scratch has no such mechanism. Retries are still bounded (10000 attempts, matching Clojure's `RETRY_LIMIT`), so a stuck transaction eventually throws rather than hanging, but nothing prevents two transactions from repeatedly colliding under adversarial timing the way barging is designed to avoid.
- **Exceptions abort immediately; only version conflicts retry.** A transaction body that throws propagates the exception right away rather than retrying (bounded at 10000 attempts, mirroring Clojure's `RETRY_LIMIT`).
- **Validators run at each `alter`/`ref-set` call, not deferred to commit.** Real Clojure validates a ref's prospective new value once at commit time, after all commutes have been re-applied against the latest committed value. Swish validates immediately when `alter`/`ref-set` is called within the transaction body — functionally equivalent for the common case, but a validator could in principle be asked to reject a value again on retry that wouldn't have been the true final value Clojure would have validated at commit.
- **No ref history retention.** `ref-min-history`/`ref-max-history` are real get/set pairs and `ref-history-count` always returns 0, but none of them affect transactional behavior. Real Clojure's history exists so an `ensure`-protected reader can be served a slightly-stale value instead of blocking on an in-progress writer's commit; Swish's optimistic-retry design (above) already never blocks readers on writers, so history has no role left to play.

### Agent lifecycle no-ops

`shutdown-agents` and `restart-agent`'s `:clear-actions` option are accepted (for source compatibility with ported Clojure code) but have no observable effect. Real Clojure's `send`/`send-off` share process-wide thread pools that `shutdown-agents` tears down, and a failed agent holds a real backlog of not-yet-run actions that `:clear-actions` can discard; Swish instead gives every agent its own dedicated GCD queue and dispatches each `send` onto it eagerly, so a "failed" action has already run (as a no-op) by the time it would matter — there is no shared executor to shut down and no held-back backlog to clear.

Real Clojure funnels every agent's actions through two shared, process-wide pools (bounded for `send`, unbounded for `send-off`) specifically because JVM threads are expensive enough to justify pooling across every agent in the process; GCD queues don't carry that same per-thread cost, so giving every agent its own dedicated serial queue was a deliberate, still-reasonable architecture choice for Swish rather than an oversight. Two consequences worth naming explicitly:
- **`set-agent-send-executor!`/`set-agent-send-off-executor!` aren't implemented at all** — there's no shared executor for them to reassign, so there's no Swish equivalent to provide.
- **Sends issued inside a `dosync` are held until commit, and sends issued inside a running agent action are held until the action completes — both now implemented, matching real Clojure's dispatch priority (transaction → running action → immediate).** The `dosync` half was the real correctness gap: `send`/`send-off` called inside a transaction is buffered on the `TransactionContext` (`Evaluator+STM.swift`'s `pendingActions`) rather than dispatched immediately, and `coreDosync` (`CoreRef.swift`) releases the buffer — dispatching each held send exactly once — only after `attemptCommit` succeeds. A retry (`continue`) or an abort (the body throws) discards that attempt's `TransactionContext` and its buffer without releasing, so a transaction that retries/aborts no longer fires its sends once per attempt. The **running-agent-action half** mirrors Clojure's `Agent.nested`: a thread-local `currentAgentActionSends` buffer (`Evaluator+Concurrency.swift`) is installed by `SwishAgent.runAction` around each action body; a nested `send` is held there (via `holdAgentActionSend`) and released (`releaseAgentActionSends`) only after the action completes successfully — discarded if the action throws (parallel to the `dosync` abort; Clojure likewise releases only when the action "changes the agent's state", i.e. doesn't error). The user-facing `release-pending-sends` (`CoreConcurrency.swift`) flushes the held nested sends immediately and returns the count (0 outside an action). In all cases send-time dynamic bindings are preserved: `coreSend` snapshots `captureCurrentBindings()` at the call site and dispatches via `SwishAgent.enqueueCaptured(…, frames:)` when the buffer releases, since the enclosing body's bindings have been popped by then. Priority is checked transaction-first, so a `send` inside a `dosync` *nested in* an agent action goes to the transaction buffer (fires on commit), matching Clojure. A nested `dosync` joins the outer transaction, so its sends fire on the outer commit.

### `tap>` never drops — its queue is effectively unbounded, unlike real Clojure's

Real Clojure's `tap>` sends values through a bounded (1024-slot) `java.util.concurrent.ArrayBlockingQueue`, drained by a single background `Thread`; `tap>` uses non-blocking `.offer`, returning `false` immediately if the queue is full instead of blocking — that's what its `true`/`false` return value actually reports (room in the queue vs. dropped). Swish's `tap>` (`CoreConcurrency.swift`) instead dispatches onto a dedicated serial `DispatchQueue` (`tapQueue`), reusing the same "dedicated serial queue + captured dynamic bindings + per-call error swallowing" pattern `SwishAgent` already established for `send`/`send-off`. GCD's own queue has no fixed capacity, so there is no equivalent backpressure: `tap>` always returns `true` and never drops a value, regardless of how slow or backed-up the registered taps are. Building a faithful bounded-queue-with-try-offer primitive was judged not worth it for this pass — the real one exists to bound memory under sustained backpressure on a long-running JVM process, a concern that doesn't come up in Swish's actual usage, and the jank suite's own `taps.cljc` fixture never exercises the drop-on-full path either.

### Future cancellation is cooperative-only (a platform limitation, not a simplification)

`future-cancel` only takes effect at explicit polling checkpoints (currently `sleep!`'s ~20ms poll loop) rather than truly preempting a running computation, unlike Java's `Thread.interrupt()`, which can unblock a thread stuck in a blocking call. This isn't a corner Swish chose to cut — it's a hard ceiling on Apple platforms, confirmed against Swift Evolution and Apple's own documentation: Swift's structured-concurrency cancellation is explicitly cooperative-only by design (SE-0304: "cancellation has no effect at all unless something checks for cancellation"), Foundation's `Thread.isCancelled` is likewise just a pollable flag, `pthread_cancel` is unimplemented on Darwin, and signal-based interruption (`pthread_kill`) is unsafe to use from Swift/GCD (handlers aren't async-signal-safe with ARC or the Swift runtime, and GCD doesn't expose the underlying `pthread_t` to signal in the first place). Swish's cooperative-polling approach is the Apple-recommended pattern here, not a workaround for a missing feature.

### Nested syntax-quote depth tracking

Syntax-quotes inside syntax-quotes (`\`\`~x`) do not increment depth — `~` always evaluates immediately regardless of nesting level. This only affects macro-writing macros. See `syntaxQuoteExpand` in `Evaluator+Destructuring.swift`.

### Syntax-quote namespace resolution uses call-site namespace for `~` unquoted values

`preExpandSyntaxQuote` (called at `defmacro` evaluation time) pre-qualifies all quoted symbols using the defining namespace. However, gensyms (`x#`) are still generated fresh at each call rather than being fixed at definition time, because pre-generated gensyms get re-qualified by the runtime expander. Functionally correct, but differs from Clojure where gensyms are stable across calls.

### `case` dispatches via a linear equality chain, not a JVM jump table

Real Clojure's `case` macro expands to a `case*` special form that the JVM bytecode compiler turns into an actual `tableswitch`/`lookupswitch` jump table (O(1) dispatch) — the exact strategy depends on hashing the test constants (`prep-ints`/`prep-hashes`/`merge-hash-collisions` in `clojure/core.clj`). Swish has no bytecode compiler, so `case` (`core.clj`, ported directly from the real source) keeps every portable part of the real macro verbatim (clause parsing, list-of-constants expansion, duplicate-test-constant detection, default-clause handling) but replaces only the dispatch-code-generation step with a `cond`-chain of `(= ge 'test)` checks. This is semantically identical — verified against every case in the jank suite's `case.cljc`, including the numeric-tower discrimination rules (`1`/`1N` match each other but not `1.0`/`1.0M`; `Double` and `BigDecimal` are mutually exclusive categories) — just O(n) instead of O(1). This doesn't cost anything relative to the rest of Swish, which has no O(1) dispatch anywhere else either (it's a tree-walking interpreter, not a compiler).

Implementing `case` also surfaced and fixed a real, pre-existing bug: `expandAliases` (`Evaluator+AliasExpansion.swift`, run on every `fn`/`defn` body to pre-qualify bare symbols to their fully-qualified var names, so closures resolve correctly even after a later namespace switch) walked into every list argument uniformly, with no awareness that a macro's arguments might be unevaluated literal data rather than code. This silently corrupted `case`'s test-constants (e.g. `list` inside a `(list of syms)` test-constant got rewritten to `clojure.core/list`) whenever `case` appeared inside a `fn` body, since `case` wasn't in `expandAliasesInExpr`'s existing `quote`/`syntax-quote`/`fn`/`let`/`loop` special-case list. Fixed by adding `case` to that same list (skip it entirely, exactly like `quote` — its own separate macro-expansion path, run later through the normal evaluation flow, correctly resolves everything when it actually executes). A broader fix (treat *any* macro call as opaque) was tried first and reverted: it broke `cond` and everything like it, since most macros' arguments genuinely are code that should be qualified — only macros with `quote`-like literal-data arguments (currently just `case`) need this treatment, and that can't be determined generically from "is this a macro," only from each macro's own semantics.

### `subvec` copies its slice instead of sharing structure with the original vector

Real Clojure's `subvec` is documented as O(1), returning a `clojure.lang.APersistentVector.SubVector` that wraps the original vector plus a `start`/`end` range — no copying. Swish's `subvec` (`CoreSequence.swift`) instead copies the sliced range into a new `.vector`, making it O(n) in the slice size rather than O(1). Same category of divergence as `case`'s O(n) dispatch above — not something worth a dedicated wrapper type for, since Swish is a tree-walking interpreter with no O(1)-dispatch machinery elsewhere either, and no other code currently depends on `subvec`'s result aliasing the original vector's storage.

### `with-precision` rounds only the body's final result, and only supports one rounding mode

Real Clojure's `with-precision` binds a dynamic var (`*math-context*`) around a body; every BigDecimal arithmetic op (`+`, `-`, `*`, `/`, `quot`, `rem`, `inc`, `dec`, `abs` — confirmed by reading `Numbers.java`, each checks `MATH_CONTEXT.deref()`) uses it when bound to round *its own* result to a given precision under a given rounding mode. Swish implements `with-precision`/`*math-context*` (`core.clj`), but with two deliberate simplifications:

- **Only the body's overall final result is rounded, not every intermediate BigDecimal operation within it.** `coreAdd`/`coreSubtract`/`coreMultiply`/`coreDivide`/`coreQuot`/`coreRem`/`coreAbs` (`CoreArithmeticBasic.swift`) are plain `([Expr]) throws -> Expr` closures with no evaluator access, so they have no way to read `*math-context*`'s current dynamic binding (which lives in evaluator-instance-scoped `bindingFrames`); giving them that access would mean threading evaluator state through the arithmetic hot path the Tier 4 performance pass specifically tuned. Instead, `with-precision`'s macro expansion (`` `(binding [*math-context* {...}] (round-with-math-context (do ~@body))) ``) rounds only what the body as a whole returns. For a body that's a single BigDecimal expression this matches real Clojure exactly; for a body chaining multiple BigDecimal ops (e.g. `(with-precision 3 (+ (* a b) (* c d)))`), Swish computes every intermediate step at full exact precision and rounds once at the end, which can give a different final answer than rounding after each step the way real Clojure does.
- **Only one rounding mode is supported** (`:HALF_UP`, or omitting `:rounding` entirely) — the package's own `withPrecision(_:)` rounds to N significant digits using exactly one fixed, hardcoded strategy (`getRoundingTerm`, HALF_UP-style: ties round away from zero) with no way to select a different mode, so any other requested mode (`UP`, `DOWN`, `CEILING`, `FLOOR`, `HALF_DOWN`, `HALF_EVEN`, `UNNECESSARY`) throws immediately rather than silently computing the wrong answer. `UNNECESSARY` is treated as just another unsupported mode (always throws) rather than its real conditional semantics (only throw if rounding would actually change the value) — a further, deliberate simplification.

**A real, previously-undocumented bug found and worked around while implementing this**: `BigDecimal.withPrecision(_:)` (`.build/checkouts/BigDecimal/Sources/BigDecimal/BigDecimal.swift`) silently fails to round negative values in cases that need to round away from zero. Its internal "does this need rounding" check (`p < 10 * r`) compares against `r`, the remainder of a `BigInt` division that truncates toward zero and so carries the sign of the input — for a negative input, `10 * r` is always negative, making the check always false, so the rounding-adjustment step is silently skipped (the result is truncated toward zero instead of rounded). Confirmed by hand-tracing `BigDecimal(-0.12355).withPrecision(3)` → `-0.123` (wrong; should be `-0.124`) against the positive case rounding correctly. Swish's `bigdec-round-to-precision` (`CoreArithmeticPrecision.swift`) works around this locally by sign-normalizing before calling `withPrecision` and re-negating after — the same trick the package's own `/` operator already uses internally, which is why plain division doesn't exhibit this bug. This is a bug in the vendored package, not something to "fix" a second time if it's ever patched upstream — check first.

### `format` follows Foundation's printf dialect, not Java's `java.util.Formatter`

Real Clojure's `format` is `(String/format fmt (to-array args))` — Java interop over `java.util.Formatter`. Swish has no JVM to delegate to, so `format` (`CoreString.swift`) is a native implementation built on Foundation's `String(format:arguments:)`, which follows a printf/CFString dialect that genuinely diverges from Java's in several ways: `%s` in the C/Darwin dialect expects a C string pointer rather than accepting any object via `.toString()`; `%n` means something different from Java's "platform newline" in classic printf (where it can mean "write the character count into a pointer argument"); there is no comma-grouping flag (`%,d`) and no positional argument references (`%1$s`) implemented. This is a permanent platform divergence, not a partial port — Swish doesn't attempt to replicate `java.util.Formatter` semantics, and the jank suite's own `format.cljc` fixture is deliberately conservative for exactly this reason (per its own comment: format compatibility varies across Clojure implementations).

Two real crashes (SIGSEGV) were found and fixed during implementation, both stemming from C varargs having no type safety — the format string alone dictates what shape of value each argument position must be, independent of the argument's own Swift type:
- `(format "%s" "hello")` crashed because a Swift `String` bridges to `CVarArg` as an object reference, but `%s` expects a raw C string pointer. Fixed by marshaling any string-shaped-directive argument through `NSString`/`.utf8String`, keeping the `NSString` alive for the call's duration.
- `(format "%s" 42)` crashed because the original marshaling was based on the *argument's* Swift type (`.integer` → native `Int`), not what the *directive* actually expects. Fixed by scanning the format string (`formatDirectiveShapes`) to classify each consuming directive as string-shaped, numeric-shaped, or no-arg, then marshaling each argument to match its directive's shape rather than its own type. A non-numeric value passed to a numeric-shaped directive (e.g. `(format "%d" "not-a-number")`) now throws a clean `EvaluatorError.invalidArgument` instead of risking undefined behavior in the other direction.

This scanner is minimal — no positional-argument support, no comma-grouping — and exists purely to make the two most natural usage patterns (`%s` on anything, numeric directives on numbers) safe, not to achieve Java-`Formatter` parity.

### `clojure.test` — `assert-expr` / `try-expr`

`is`'s general (non-`thrown?`) case now dispatches through a real `assert-expr` multimethod (`test.clj`), following the same `defmulti`/`defmethod` pattern already established by `report` and `use-fixtures`. A `:default` method fixes the previously-documented bug where failure output showed `(not false)` (a re-evaluated, opaque boolean) instead of `(not (= 5 4))` (the quoted source form) — the fix is to quote the form once at macro-expansion time rather than splicing it back in as code to re-run. A `'=` method goes further, evaluating each side of `=` exactly once and reporting the real runtime values (e.g. `(not (= 5 4))` using the actual values `x`/`y` held, not their symbol names) — the "richer, both sides" feature this gap previously referred to. Since `are` was rewritten to use real `do-template` substitution (below) instead of wrapping every row in a `let`, this richer display now fires for `are`-driven equality checks too, not just bare `(is (= ...))` — `assert-expr` sees the substituted `(= 5 4)` directly rather than a `let`-buried form.

Two deliberate scope boundaries, not oversights:
- **`is`'s bare `thrown?`/`p/thrown?` handling stays outside `assert-expr` dispatch**, as a single hardcoded `cond` branch in `is` itself, unchanged. (A second branch used to exist for `(let [...] (thrown? ...))`, needed only because the old `let`-based `are` buried `thrown?` calls inside a `let`; now that `are` substitutes directly instead, that shape never occurs and the branch was removed.)
- **`thrown?` still doesn't check the exception type** — `c` in `(thrown? c body)` is parsed but discarded (unchanged from before); Swish's `catch` special form only ever matches the literal symbol `Exception` (`Evaluator+TryCatch.swift`), so there's no dispatchable exception-type hierarchy to check against regardless. `thrown-with-msg?` is now implemented (see the `ex-info`/`ex-message` entry below) with the exact same class-argument-discarded limitation.

Implementing this surfaced a Swish-specific namespace-qualification gap — see "Macro-adjacent code needs explicit namespace qualification" below, which explains why `assert-expr`'s methods reference `do-report` as `clojure.test/do-report` rather than bare.

### `ex-info`/`ex-message`/`ex-data`/`ex-cause`, and `thrown-with-msg?`

Previously an entirely undocumented gap (not something this file had flagged): `throw`/`catch` had no structured-exception concept at all. `(throw expr)` wraps any bare `Expr` in `struct SwishException: Error { let value: Expr }` (`SwishException.swift`), and `catch Exception e#` binds `e#` to whatever was thrown, or to `.string("\(error)")` for a native `EvaluatorError` (`exprForError`, `Evaluator+TryCatch.swift`) — no `ex-info`/`ex-message`/`ex-data`/`ex-cause` existed anywhere, despite being functions almost all idiomatic Clojure error-handling code relies on.

`ex-info`/`ex-message`/`ex-data`/`ex-cause` are now implemented as pure `core.clj` code (`;;; Exceptions` section), following the same precedent Multimethods/Protocols established — no new `Expr` case. `(defrecord ExceptionInfo [message data cause])` gives `ex-info` values a real, dispatchable type identity via `instance?` (an exact type-name match against `.record`'s `typeName`, per Protocols' documented exact-match-only dispatch), matching real Clojure's `ExceptionInfo` being a distinct class. `ex-info` doesn't validate that `data` is a map (unlike real Clojure, which throws `IllegalArgumentException` for a non-associative `data`) — a deliberate, unenforced-simplification in the same spirit as `into-array`'s unenforced `type` argument.

**`ex-message`'s fallback for non-`ExceptionInfo` values is the one real Swish-specific semantic call, not just a straightforward port**: real Clojure's `ex-message` works on *any* `Throwable` via `.getMessage()`; Swish has no such generic mechanism. Instead, `ex-message` returns `(:message e)` for an `ExceptionInfo`, `e` itself when `e` is a plain string, or `nil` otherwise. The plain-string fallback isn't arbitrary — it's the pre-existing, already-used Swish idiom (`assert`'s and `with-precision`'s own error paths already do `(throw (str "..."))`), and critically, `exprForError` already converts *every* native `EvaluatorError` to exactly this shape before `catch` ever sees it — so this one fallback rule transparently covers both "user threw a string" and "a native runtime error was caught," not just `ex-info` values. `ex-data`/`ex-cause` return `nil` for anything that isn't an `ExceptionInfo` (matching real Clojure's fallback-to-nil for a non-`ExceptionInfo` `Throwable`) — Swish has no generic cause-chain concept beyond whatever `ex-info` was explicitly given.

**`thrown-with-msg?`** (`test.clj`'s `is` macro, a `cond` branch alongside the existing `thrown?` branch) discards its class argument for exactly the same reason `thrown?` already does (documented above) — `catch`'s type matching is a hardcoded literal-string comparison against `"Exception"` (`Evaluator+TryCatch.swift`), not a dynamic dispatch on whatever symbol is written in source, so there's nothing to check the class argument against, and evaluating it would fail outright for a real-Clojure JVM class name (`ArithmeticException`, etc.) that doesn't exist in Swish. Only the message check is real: `(and (ex-message e#) (re-find pattern (ex-message e#)))`, guarding against calling `re-find` with a `nil` message (a message-less caught value fails the assertion instead of crashing the test runner).

**A separate, previously-undiscovered bug was found and fixed while implementing this**: uncaught-exception printing was broken for *every* thrown value, not just future `ex-info` ones. Confirmed by building and running the REPL before the fix: `(throw (str "boom"))` printed `❌ SwishException(value: string)`; `(throw (Foo. 1 2))` printed `❌ SwishException(value: user/Foo)` — `Repl.swift` and `CLI.swift` interpolated the raw Swift `Error` (`"\(error)"`, Swift's default struct-reflection format) instead of routing the caught `Expr` through the existing printer. Fixed with a new `Swish.describeError(_:) -> String` (`SwishKit.swift`), which runs `exprForError`'s result through `Printer.strString` (the `str`-style unquoted formatter, not `printString`/`pr-str`'s quoted form — so `(throw "boom")` now displays as `boom`, not `"boom"`) — both `Repl.swift`'s `printError` and `CLI.swift`'s file-run error path now use it.

### `clojure.template/do-template`

Implemented (`Sources/SwishKit/Resources/clojure/template.clj`), backed by a minimal `clojure.walk` port (`walk.clj`) providing just `walk`/`postwalk`/`postwalk-replace` — the three functions `do-template`/`apply-template` actually need, not the full `clojure.walk` namespace (no `prewalk`, `stringify-keys`, `macroexpand-all`, etc.). `walk`'s collection dispatch is narrowed to `list?`/`vector?`/`map?`/`set?` — real Clojure's `walk` also special-cases `IMapEntry`/`IRecord`, which only matter when walking *runtime data* (a realized map's entries, a `defrecord` instance); a macro template is unevaluated reader syntax and is never shaped like either, so this narrowing loses nothing for the port's actual use.

This wasn't just a naming gap: real `do-template` does pure textual substitution (no enclosing `let`), so it reaches *inside* `quote` — `'arg` becomes `'def`, `'do`, etc. Swish's old `let`-based `are` couldn't do this (`let` doesn't rebind what's inside a quoted form), which is why `support/clojure/core_test/special_symbol_qmark.cljc` existed — a Swish-specific overlay working around exactly this, by quoting each template *value* instead of the template *variable*. With real substitution now reaching inside `quote`, the upstream (unshadowed) test passes as-is; the overlay was verified against the full jank suite (both with and without it — 0 failures/errors either way) and deleted.

`clojure.test/are` is now `` `(temp/do-template ~argv (is ~expr) ~@args)`` — matching real Clojure's actual implementation exactly (verified against the real source, not from memory) — replacing the old `partition`+`interleave`+`let` expansion.

**A real bug found while implementing this**: an initial, more upstream-literal port of `walk`/`postwalk` (using `map`/`mapv` to rebuild collections and `partial` for `postwalk`'s self-recursion, mirroring real Clojure's own structure) segfaulted with a stack overflow when run under Swift Testing's test-runner thread — reproducible even on something as shallow as substituting into `(p/thrown? (/ x 0))` (only 2 levels of nesting), and confirmed as a stack-depth issue by reproducing the same crash outside the test harness with `ulimit -s 512`. `swift run`'s own thread has enough default stack headroom to mask it, but the test runner's thread doesn't. Root cause: `map`/`filter` are lazy `core.clj` defns composing multiple independently-recursing layers (see "Interpreter has a high per-element constant cost for lazy-seq-driven code" below) — for a form this small the wall-clock cost is negligible, but the *native Swift call-stack depth* it adds per logical recursion level is not, and stacks on top of `walk`'s own (unavoidable, but shallow) nesting recursion. Fixed by rebuilding collections with `reduce` (a native, non-lazy function) instead of `map`, and having `postwalk` recurse directly instead of through `partial`.

### Macro-adjacent code needs explicit namespace qualification

A literal symbol embedded in a `defmacro`'s own syntax-quote template gets pre-qualified to the macro's defining namespace once, at definition time (`preExpandSyntaxQuote`) — this is why, for example, `is`'s own `` `(do-report ...) `` calls (in its unchanged `thrown?` branch) resolve correctly no matter what namespace calls `is`. Two related shapes *don't* get this treatment, and need the namespace spelled out explicitly (`clojure.test/do-report`, not bare `do-report`) to avoid an `Undefined symbol 'user/do-report'`-style error the first time the code runs from a namespace other than the one it was defined in:

- **A `defmethod` body** (or any ordinary function that happens to construct and return a syntax-quote template) — it's an ordinary function, not a `defmacro`, so `preExpandSyntaxQuote` never runs on it; its template's bare symbols resolve against whatever namespace is current when the method actually executes (the caller's), not the namespace it was defined in. Hit by `assert-expr`'s `:default`/`'='` methods.
- **An unquoted (`~`/`~@`) sub-expression nested inside an otherwise-quoted `defmacro` template** — `preExpandSyntaxQuote` only pre-qualifies symbols that end up literally embedded in the output template; it doesn't reach into unquote, which is ordinary executable code evaluated immediately during expansion. Hit by `try-expr`'s `~(clojure.test/assert-expr msg form)` and `do-template`'s `~@(map (fn [a] (clojure.template/apply-template argv expr a)) ...)`.

Confirmed twice now (`assert-expr`/`do-report`, then `do-template`/`apply-template`) — enough to name as a real, recurring pattern, but not yet enough to justify changing the underlying mechanism (`expandAliases`, `Evaluator+AliasExpansion.swift`). That function runs on every `fn` evaluation interpreter-wide, not just `clojure.test`/`clojure.template` code, and has already caused one revert-worthy bug once (a broader "treat any macro call as opaque" fix, tried during the `case` implementation, broke `cond` and had to be reverted — see the `case` section above). Deliberately deferred until it's worth its own dedicated design and full-suite verification pass, not a rushed add-on to unrelated feature work.

### `run-tests` uses `reduce` + `merge-with` instead of real Clojure's `apply merge-with +`

The original reason for diverging here (`asSequence` silently swallowing lazy-seq thunk errors) is fixed — see that section above. Reverting to real Clojure's exact idiom, `(apply merge-with + (map test-ns namespaces))`, was tried directly and found to **segfault with a stack overflow under Swift Testing's runner thread** (confirmed against the real test runner, not just the `ulimit`-based reproduction technique — that technique turned out to crash the *original*, already-working code too under an overly aggressive constraint, making it unreliable for this specific comparison; the real Swift Testing thread's actual, less extreme stack budget is what distinguishes the two). This is the same class of issue as `clojure.walk`'s `postwalk` (below): calling a variadic user-defined function (`merge-with`) through `apply` from this position costs more native Swift call-stack depth than the equivalent operation's wall-clock cost would suggest, and the smaller-than-`swift run` runner-thread stack is what actually surfaces it — `apply merge-with +` alone (top-level, not nested inside `run-tests`'s own call frame) and `(map test-ns namespaces)` alone both work fine in isolation; only the combination, nested at this call depth, crashes.

`run-tests` now uses `(reduce #(merge-with + %1 %2) *initial-report-counters* (map test-ns namespaces))` — logically identical to real Clojure's merge (still calls `merge-with` once per namespace, same accumulated result), confirmed crash-free under the real test runner, and confirmed correct via a new multi-namespace regression test (the existing tests only ever exercised `run-tests` with a single namespace, so the actual cross-namespace merge behavior had never been directly tested before). `doall` is no longer needed either way — `reduce` already consumes `(map test-ns namespaces)` lazily without it, unlike `apply`, which must fully realize its final argument up front.

`run-all-tests`'s regex-filter arity had its own, separate, bigger-than-expected problem discovered during this same pass: it called `re-find`, which — like `re-matches` — **does not exist in Swish at all** (confirmed by direct eval: `Undefined symbol`). Swish has the regex *literal* type (`#"pattern"`, `SwishRegex.swift`) and uses it internally for `clojure.string/replace`/`split`, but exposes no general-purpose regex-matching function to user code — see the new dedicated entry below. `run-all-tests` was never actually invoked anywhere in this repo, so this had never surfaced. Fixed narrowly (not by implementing general `re-find`/`re-matches`) with a new `swish-regex-whole-match?` primitive built specifically for this one caller, using `String.wholeMatch(of:)` against the same `SwishRegex`-wrapped `Regex<AnyRegexOutput>` `split`/`replace` already use — deliberately not named `re-matches`, so it doesn't imply real `re-find`/`re-matches` (capture groups, `re-seq`, `re-pattern`, etc.) exist.

### `re-pattern`/`re-matches`/`re-find`/`re-seq` + stateful matchers (`re-matcher`/`re-groups`/1-arg `re-find`)

`re-pattern`, `re-matches`, `re-find`, `re-seq`, `re-matcher`, and `re-groups` are implemented natively (`Sources/SwishKit/Core/CoreRegex.swift`), matching real Clojure's argument order (`re` first) and nil/bare-string/vector result-shape rules: no match → `nil`; a match with no capture groups → the bare matched string; a match with capture groups → a vector `[whole g1 g2 ...]`, with a non-participating (unmatched optional) group as `nil` in its slot (the shared `regexMatchResult(_:in:)` helper produces this shape for every regex fn). `re-matches` anchors at both ends of `s` (`String.wholeMatch(of:)`); the 2-arg `re-find` matches anywhere (`String.firstMatch(of:)`). All build on the same `Expr.regex(SwishRegex)`/`Regex<AnyRegexOutput>` machinery `clojure.string/replace`/`split` already used internally.

**Stateful matchers** close what were previously the two scoped gaps here. `(re-matcher re s)` returns a `SwishMatcher` (`SwishMatcher.swift`), a mutable cursor; `(re-find m)` (the 1-arg form — `re-find`'s arity is now `.atLeastOne`, dispatching on arg count) advances it to the next match or `nil` at exhaustion; `(re-groups m)` returns the most recent match's result (throwing if none is current, mirroring Java's `IllegalStateException`). Design notes:
- **A matcher is its own `Expr` case (`.matcher(SwishMatcher)`), not a repurposed atom/map.** This matches how every other stateful reference cell (`atom`/`ref`/`future`/`promise`/`delay`/`transient`) is modeled, and — unlike an atom-backed representation — keeps `atom?`/`deref` correctly *false*/unsupported on a matcher, as in real Clojure (where a `Matcher` is neither). `(type m)` ⇒ `:matcher` (vs Java's `Matcher` class — the visible seam). Adding the case is mechanical ripple across `Expr`/`Expr+Equatable`/`Expr+Hashable` (identity-based, like the other reference cells)/`Expr+Description`/`Printer`/the `eval` self-eval list; no other exhaustive `Expr` switch needed it.
- **Matches are precomputed eagerly at `re-matcher` time** via `s.matches(of: re.regex)` — the *same* whole-string-scoped API `re-seq` uses, and for the same reason (see the `re-seq` bullet below): `firstMatch(of:)` on a chopped `Substring` re-anchors `^` to the substring's local start, so a cursor advanced by re-slicing would be wrong. The matcher therefore just walks a fixed, pre-formatted `[Expr]` list, so `(re-find m)` is O(1) and its left-to-right non-overlapping sequence matches Java's repeated `find()`. Same eager-not-lazy tradeoff as `re-seq`: a matcher over a huge string does the full match scan up front. Not thread-safe (Java's `Matcher` isn't either); the backing `Mutex` guards only against memory corruption.

`re-find`'s 1-arg `Matcher`-only stateful *stepping* (Java's `re-matcher`+`.find()` region cursor advancing through the live string) is thus provided in the precompute-then-walk form above; `thrown-with-msg?` remains as noted elsewhere. One remaining scope boundary:
- **`re-seq` is eager, not a true incrementally-realized lazy sequence** — a deliberate, measured divergence, not an oversight. It's implemented via `s.matches(of: re.regex)` (the same whole-string-scoped API `clojure.string/replace`/`split` already use), computing the full match list up front and wrapping it in an ordinary `.seq`. The alternative — chopping `s` into successive substrings and re-running `firstMatch(of:)` on each remainder to get genuine incremental laziness via `lazy-seq` — was tried and empirically confirmed **unsafe**: Swift's `Regex<AnyRegexOutput>.firstMatch(of:)` re-anchors `^` to a `Substring`'s own local start rather than continuing to treat the original string's start as the sole `^` anchor point (confirmed with a standalone probe: `^\d` against `"123"` chopped repeatedly after each match finds 3 matches, one per digit, instead of the correct 1 — diverging from Java's `Matcher.find()` region-anchoring semantics that real Clojure relies on). `s.matches(of:)`, by contrast, operates on the whole original string throughout and gets `(re-seq #"^\d+" "1 2 3")` right (exactly one match, `"1"`) — but at the cost of full-string eagerness: `(take 3 (re-seq re huge-string))` does the full match-scan up front instead of stopping after 3 matches. `seq?` is still `true` on the result (an ordinary `.seq`, not `.list`), matching real Clojure, but `lazy-seq?` is `false` where real Clojure would report `true` — that's the visible seam of this divergence.

`swish-regex-whole-match?` (`CoreStringNS.swift`) predates this work and is functionally unchanged — still used by `run-all-tests`'s regex-filter arity (`test.clj`) — but is now redundant with `re-matches` for new code; its comment has been updated accordingly rather than removing it, to avoid touching `test.clj`'s call site as part of unrelated work.

### Interpreter has a high per-element constant cost for lazy-seq-driven code (not an O(n²) bug)

Swish's tree-walking interpreter costs roughly 300–475µs per element for chains like `filter`/`range`/`vec`+`seq`+`next`-walks — confirmed **linear** (not quadratic) by direct measurement with the built binary (excludes `swift run`'s own overhead): `(count (filter (fn [_] false) (range n)))` at n = 2000/4000/8000/16000/32000 scales almost exactly proportionally to n (8000→3.88s, 16000→7.73s, 32000→15.16s). A separate check — `(dorun (seq (vec (range n))))`, the pattern most likely to hit an `Array(dropFirst())`-copy-per-`next`-call cost — going from 16000→64000 (4x) took only ~3.2x longer, again linear. There is no O(n²) bug in these paths (an earlier, unverified claim to this effect was wrong and has been corrected here).

**Since profiled** (a structural code audit plus release-build measurements — n=20000, `count`/`dorun` over `range`): a pure `loop`/`recur` baseline with zero lazy-seq involvement costs only ~4.9µs/element (100k iterations in 0.489s), ~20-100x cheaper than the lazy-driven figure above — ruling out generic environment-lookup/evaluator-dispatch overhead as the dominant cause, since that baseline exercises both too. The real driver: `range`, `filter`, `map`, `iterate`, `take-while` etc. are all ordinary interpreted `defn`s, not special-cased lazy machinery — `lazy-seq` itself is the only actual special form involved, and does no per-element work of its own. Realizing one lazy element means running a full recursive interpreted call graph, and cost compounds multiplicatively with how many separate lazy layers that graph composes through. Measured directly: `range`'s 1-arg form used to be `(take-while #(< % end) (iterate inc 0))`, composing **two** independently-recursing interpreted functions, each wrapping its own `LazySeqBox`, costing ~94µs/element, vs. the 3-arg form's single self-recursive `(lazy-seq (let [pred ...] (when (pred start) (cons start (range ...)))))` costing ~21µs/element for the identical logical sequence — a measured **4.5x** difference attributable purely to composition depth. **Fixed**: the 1-arg/2-arg forms now delegate to the 3-arg form (`step` fixed at `1`, matching `repeat`/`cycle`'s existing single-layer style) instead of composing `take-while`+`iterate` — confirmed via a release-build before/after measurement on `(count (filter (fn [_] false) (range 32000)))`: ~3.85s → ~2.15s (~44% wall-clock reduction on this combined benchmark; the pure per-element figure above is the more isolated 4.5x). This generalizes beyond `range`: any core.clj sequence function built by composing multiple lazy layers (rather than one self-recursive `lazy-seq`) pays a per-layer interpreter tax on every element — `range` was just the concrete, measured instance.

**`LazySeqBox`'s `NSLock` was investigated as a `Mutex` swap candidate and rejected** — measured, not just deferred. `LazySeqBox.swift` still uses `NSLock`, not `Synchronization.Mutex` like the rest of the codebase (confirmed an oversight, not a deliberate choice, via git history: the commit that introduced `Mutex` everywhere else, `c511047`, "Thread-safety retrofit," 2026-07-14, never touched this file). A full conversion was prototyped and empirically tested (a standalone repro of the exact rewrite, run at multiple chain depths) rather than reasoned about in the abstract: converting the ordinary lock/unlock sites (`realizeIfNeeded`, `resolveChain`, `backfill`/`backfillError`, `isRealized`) to `Mutex.withLock` is safe, but converting the custom `deinit` (which iteratively unlinks a long realized `LazySeqBox` chain to avoid the stack-overflow-prone recursive ARC teardown documented below) the same way **reintroduces essentially the same stack overflow**, crashing at ~30,000-40,000 chain depth instead of surviving 1,000,000+ — `Mutex` has no lock-free escape hatch, and this `deinit`'s stack-safety specifically depends on plain, non-opaque field mutation the optimizer can see through, which `Mutex.withLock`'s generic closure boundary defeats. No partial-conversion path exists (`Mutex` can't be bypassed for just one method on the same field). Left on `NSLock` — this is now a measured, deliberate choice, not an oversight to revisit casually.

**`DelayBox`'s `NSLock` was the same-shaped sibling flagged above, and its conversion was investigated and found safe.** Unlike `LazySeqBox`, `DelayBox` holds a single `Expr` (a `delay`'s memoized result), not a chain of boxes — it has no custom `deinit` at all, so there's no chain-unlinking logic for `Mutex.withLock`'s closure boundary to defeat. Converted (`DelayBox.swift`) to `Mutex<State>`, matching the pattern already used by `Var`/`SwishAtom`/`SwishRef`/etc.: `force()`'s existing read-or-claim-then-run-unlocked-then-store structure carries over exactly (the thunk still runs with the lock released, since it's arbitrary user code that could itself call back into `force()` on a self-referential delay), just expressed as `Mutex.withLock` closures instead of manual `lock()`/`unlock()`.

`next`-based walks (`dorun`) cost modestly more than `asSequence`-based walks (`count`) — ~104µs vs ~97.5µs/element — because `coreNext` (`CoreSequenceCore.swift`) forces one element further ahead than logically needed (to check for emptiness) and allocates an extra wrapper `LazySeqBox` on top; a real but minor (~7%) factor, not the main story, and not yet addressed. Global-symbol resolution (any reference to a builtin like `seq`/`first`/`cons`/`rest` from within a lazy body) used to cost ~10 uncached `Mutex` lock/unlock pairs per reference with no caching at any layer — **fixed**, see the "global-symbol resolution" item below (~10 locks → ~5, plus a measured ~30% wall-clock improvement on this same benchmark family).

### `LazySeqBox` needed a custom `deinit` to avoid stack overflow on releasing long realized chains

`next`/`seq` (`CoreSequence.swift`) memoize each realized step as `.cons(head, tail: .lazySeq(nextBox))`, forming a genuine singly-linked chain of `LazySeqBox` objects once fully walked (e.g. by `dorun`). Since `Expr` is an `indirect enum` (heap-boxed), Swift's compiler-generated `deinit` for a long reference chain like this is not tail-call-optimized — releasing the head recursively released the next link, which recursively released the next, etc., one native stack frame per link, crashing at ~20000 elements (confirmed via `(dorun (range n))`, independent of any lazy-seq *forcing* logic — a bare, already-realized chain crashed purely on release). Fixed with a custom `deinit` on `LazySeqBox` (`LazySeqBox.swift`) that iteratively unlinks the tail chain (using `isKnownUniquelyReferenced` to only detach links nothing else is aliasing) before default ARC teardown runs — the standard fix for this well-known Swift pattern.

### `into-array`'s `type` argument is accepted but not enforced

Real Clojure's `into-array` (`([type aseq])` 2-arity form) uses `type` to pick the JVM array's component type, and validates every element in `aseq` is compatible with it (class objects for primitives obtained via e.g. `Integer/TYPE`). Swish's `SwishArray` (`Expr.swift`) is untyped — a plain `[Expr]` wrapper with no component-type field at all — so `into-array` (`CoreSequence.swift`) accepts the optional `type` argument purely for call-site source compatibility with ported Clojure code, but never inspects or validates it. Same category of simplification `int-array`/`object-array` already made silently (neither validates its elements are actually ints/objects either); `into-array` doesn't introduce a new kind of divergence, just extends the existing one to the 2-arity form.

One consequence worth naming: real class-reference symbols like `Integer/TYPE` or `String` won't resolve if actually passed as `type`, since Swish has no vars for JVM classes at all — this fails at ordinary symbol-resolution time before `into-array` ever runs, same as any other Java-interop reference in Swish today (see the Protocols section above for the same underlying "no JVM class hierarchy" limitation). Passing a keyword or `nil` as a stand-in `type` marker works fine, since it's never inspected.

## Deferred Performance/Architecture Items

A refactoring audit (2026) covered `Sources/` (excluding `Tests/`, which served as the regression gate) for oversized functions/files, duplication, and performance opportunities. Most findings were fixed directly; the remaining items here were deliberately deferred because each needs a real design change rather than a contained, mechanical fix. Re-verify against current source before acting on any of these — this list is a map of where to look, not a guarantee the code hasn't shifted since.

`cons`/`conj` onto a list being O(n) instead of O(1) was on this list and has since been fixed: `Expr.list` is now backed by `SwishPersistentList` (`SwishPersistentList.swift`), a real cons-cell persistent list with O(1) `cons`/`first`/`rest`/`count`, matching `clojure.lang.PersistentList`'s design.

### `Environment` pays a `Mutex` acquire/release at every level of the lexical scope chain

`Environment.get` (`Evaluator/Environment.swift`) walks its `parent` chain on a miss, and each level's `bindingsState.withLock { ... }` is a full `Mutex` lock/unlock — even though the overwhelming majority of `Environment` instances (a `let`/`fn` call's locals) are only ever touched by the single thread that created them and never shared. A lookup that walks N scope levels to find (or fail to find) a binding pays N lock operations. A faster design would need to distinguish "this environment can only ever be touched by its creating thread" from the cases that genuinely need synchronization (if any — Swish's evaluator doesn't currently share a running call's environment chain across threads at all), which is a real design question, not a mechanical swap.

### `currentNs()` does two locked dictionary lookups on every unqualified symbol resolution that falls through to it

`currentNs()` (`Evaluator+Namespaces.swift`) does `findNs("clojure.core")!.findVar(name: "*ns*")!` — a locked lookup into `Evaluator.namespacesState`'s dictionary, then a locked lookup into that namespace's own var table — every time it's called, which includes every `eval` of a bare symbol not found in the local `Environment` chain (`Evaluator.swift`'s `.symbol` case) and not resolved as a qualified var. The code already carries its own comment on `setCurrentNs` explaining why this isn't trivially fixed: `*ns*` is a normal (non-dynamic) `Var`, so `in-ns` mutates one shared root value rather than a real thread-local binding, and making it genuinely dynamic/thread-local is explicitly deferred "to whichever later step first introduces real background execution." This item is that same deferred work, viewed from the performance angle rather than the correctness angle.

### `evalList`'s special-form dispatch was a 20-way sequential string comparison — fast-path guard added, but the measured win is modest

`evalList` (`Evaluator.swift`) used to match `head` against 20 literal special-form symbols (`"quote"`, `"syntax-quote"`, `"def"`, `"if"`, `"do"`, `"let"`, `"letfn"`, `"loop"`, `"recur"`, `"fn"`, `"defmacro"`, `"var"`, `"ns"`, `"lazy-seq"`, `"delay"`, `"binding"`, `"throw"`, `"try"`, `"defrecord"`, `"deftype"`, `"extend-type"`, `"extend-protocol"`) one `case .symbol("x", _):` at a time before falling to `default:` — every ordinary function call (`(+ 1 2)`, `(my-fn x y)`, `(map f coll)`, the overwhelmingly common case) failed all 20 comparisons before reaching the actual call path. Fixed by adding a `guard case .symbol(let name, _) = head, Evaluator.specialFormNames.contains(name) else { /* straight to the call path */ }` immediately before the switch — the switch and all 20 cases are otherwise untouched, so this is correctness-preserving by construction (the guard's `else` branch is byte-for-byte the switch's own pre-existing `default:` case).

**Measured, not assumed — and the result is humbler than the theoretical argument suggested.** Release-build before/after on two benchmarks: the same `(count (filter (fn [_] false) (range 32000)))` pattern used for the `range`/global-symbol-cache measurements (~2.18s → ~2.15s, ~1.5%), and a more targeted pure-ordinary-call benchmark, `(loop [i 0 acc 0] (if (< i 1000000) (recur (inc i) (+ acc i)) acc))` (~3.33s → ~3.27s, ~1.7%). Both real, both in the same direction, both far smaller than `range`'s 44% or the global-symbol-cache's 30%. Plausible reasons this pans out smaller than the O(1)-hash-vs-O(20)-comparisons argument implied: `evalList`'s dispatch is likely a small fraction of the total per-call cost (environment creation, argument evaluation, function invocation dominate), and Swift's compiler may already generate reasonably efficient code for a chain of short-string-literal pattern matches even without a true jump table. Kept anyway — it's a real, if modest, win with zero behavior risk — but this is exactly the outcome CLAUDE.md's own "measured, not assumed" standard exists to catch: the theoretical case for this fix was more compelling than its actual impact.

**The switch itself was later extracted out of `evalList` into a separate `evalSpecialForm(_:_:in:)`, for stack depth (not speed).** Adding `reify` as a 25th case surfaced this: in the **debug** build the tests run under, `evalList`'s frame allocates space for the whole switch, so *every* recursive `evalList` frame — including the ordinary-call frames that return in the guard above and never touch the switch — carries that cost, and `evalList` is the deepest-recursing function in the interpreter. One extra case grew the frame just enough to push `runTestsMergesAcrossMultipleNamespaces` (a deliberately stack-marginal multi-namespace `run-tests` test, already documented as living at the runner thread's stack edge — see the `run-tests` section) from passing into a hard SIGBUS stack overflow on Swift Testing's smaller-stack runner thread — reproduced 3/3 with the case vs. 0/3 without, and pinned to `evalList` specifically by bisection (reverting only that file cleared it) plus a crash-report backtrace showing pure `eval`→`evalList`→`evalBinding`/`evalLet` recursion bottoming at that test, with none of the reify/protocol code in it. Moving the switch into its own function makes `evalList`'s hot ordinary-call frame small again (it becomes: guard, then a tail call to `evalSpecialForm` only for actual special forms), which *more* than absorbs the reify case — net headroom went up, not down, since ordinary-call frames (the vast majority in any deep recursion) no longer pay for the switch at all. The one extra `evalSpecialForm` frame is paid only when a special form actually runs. No `@inline(never)` is needed: debug builds don't inline it back (which is where the overflow lived), and release builds have small enough frames that it never mattered there. This is the durable fix for the whole class of problem — any *future* special form added to the switch now costs `evalSpecialForm` frame growth, which the deep ordinary-call recursion doesn't multiply, rather than `evalList` frame growth, which it does.

### `fn` literals redo static analysis on every evaluation, not just once per definition

`evalFn`/`buildFnArity` (`Evaluator+FnDef.swift`) run destructuring expansion (`expandDestructuredParams`), tail-position `recur` validation (`validateRecurTailPosition`), local-name collection (`collectAllParamLocals`), and full alias-expansion (`expandAliases`) over the `fn` form's parameter vector and body — every single time that `fn` *literal* is evaluated, not once per logical definition. This matters whenever a `fn` literal sits inside a body that runs repeatedly — e.g. `(fn [y] (+ x y))` inside `(defn make-adder [x] (fn [y] (+ x y)))`, re-analyzed on every call to `make-adder` even though the inner literal's params/body syntax never changes across calls. All of this analysis depends only on the literal `fn` form itself (its AST), never on the runtime `env`/captured values, so it's a legitimate caching target — but caching needs a stable per-AST-node cache key, and `Expr` currently has no node identity to hang a cache on (equal-by-value `Expr`s from two different source locations would collide), so this is a real design question about how (or whether) to give specific `Expr` nodes identity, not a one-line memoization.

### Global-symbol resolution (e.g. `seq`, `first`, `cons` referenced by name) — was ~10 uncached `Mutex` locks per reference, now cached

Every reference to a builtin by name that isn't a local binding — the overwhelmingly common case inside lazy-seq bodies and anywhere else interpreted code calls a core function — used to re-resolve "what Var does this name refer to" from scratch on every single evaluation, with no caching at any layer. Traced precisely for the dominant case (a symbol already qualified by alias-expansion, e.g. `clojure.core/first`, evaluated via `eval`'s `.symbol` case, `Evaluator.swift`): `env.get(name)` miss (2 locks) → `resolveQualifiedVar` (`Evaluator+Namespaces.swift`): `currentNs()` [3 locks — `namespacesState` + `clojure.core`'s own `state` + the `*ns*` Var's own `state`, corrected from an earlier undercount of 2] → `findAlias` miss [1 lock] → `findNs` [1 lock] → `findVar` [1 lock] = 6 locks → `dynamicValue(of:)`: `isDynamic` + `value` [2 locks] = **≈10 lock/unlock pairs per reference** before this fix.

Fixed with a `qualifiedVarCache: Mutex<[String: Var]>` on `Evaluator`, checked first in `resolveQualifiedVar`, requiring **no invalidation logic at all** — verified against current source, not just assumed: `Namespace.intern` always reuses the existing Var object for an already-home mapping (only `.value` changes, never identity), `Namespace.refer` throws rather than silently replacing a differing Var, and there is no `ns-unmap`/`remove-ns`/any other API anywhere that deletes a namespace's var mapping — `in-ns`/`create-ns` on an existing name is guaranteed to return the *same* `Namespace` object (`findOrCreateNs`), never a new one. Only cached when both hold: (1) resolution went through the literal-namespace-name branch (`findNs`), never the alias branch (`currentNs().findAlias`) — an alias like `str` means different things depending on the *caller's* current namespace, so caching an alias resolution under its bare alias text would leak one caller's meaning into every other caller's; (2) the resolved Var's home namespace is the namespace searched (`v.namespace === ns`) — a referred (non-home) var can later be shadowed by a local `def`, which creates a genuinely new Var, so referred-var resolutions are never cached. `Var.dynamicValue`'s two separate lock acquisitions (`isDynamic`, then `value`) were also combined into one (`Var.snapshotIsDynamicAndValue()`). Net: ~10 locks → ~5 for the cached case.

**Measured, not assumed**: on the same `(count (filter (fn [_] false) (range 32000)))` benchmark used to establish the original per-element cost figures above, wall-clock time on a release build dropped from ~5.6s to ~3.9s (~30%) across repeated runs.

### Pasting a large multi-line form into the REPL costs O(n²) in the pasted text's length

`Repl.swift`'s `readMultilineInput` calls `continuationNeeded(input)` (and, each time another line is added, `computeIndent(input, ...)`) — both in `ReplInputScanner.swift` — once per line of input added to the in-progress multi-line form. Both functions unconditionally scan `input` from `input.startIndex`; neither is incremental or resumes from where the previous call left off. So pasting (or typing) an N-line form triggers N full rescans of the accumulated text — total scanned-character count grows like 1+2+...+N, i.e. O(n²) in the pasted text's total length, even though the total real work (recognizing when brackets balance) is O(n). Not yet reproduced at a pasted size large enough to be perceptible (small/medium forms are cheap enough that this is invisible), so the actual user-facing impact is unconfirmed — but the mechanism is real and would need either incremental re-scanning (track depth/position across calls instead of recomputing from scratch) or scanning only the newly-added suffix plus carried-over state.
